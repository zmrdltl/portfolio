# 개발 원칙

구현 속도보다 문제와 완료 조건을 먼저 분명히 하고, 코드·문서·테스트·리뷰가 같은 기준을 따르도록 작업합니다. AI 도구는 문제 분해와 구현 보조에 활용하되, 요구사항·기술 판단·코드 리뷰·테스트 기준·릴리스 결정은 직접 수행합니다.

## 핵심 원칙

### 1. 증상과 원인을 구분하고 수정 범위를 정합니다

느리거나 실패하는 경로를 한 가지 원인으로 단정하지 않습니다. 동시성 경합과 고정 시간창의 대기 문제를 분리한 [ClumL 외부 LLM API 호출량 제어 수정](experience/cluml.md)처럼 원인을 나눈 뒤, 직접 수정할 부분과 바꾸지 않을 부분을 정합니다.

### 2. 완료 조건을 테스트할 수 있게 만듭니다

API 성공 여부만 보지 않고 응답 형태, DB 쓰기·읽기, 화면 분기, 예외 처리를 확인합니다. [티맥스클라우드의 배포 전 생성 API 테스트 기능](experience/tmaxcloud.md), [GlueSQL 회귀 테스트](opensource/gluesql.md), [Coupler 릴리스 확인](projects/coupler.md)이 이 원칙을 적용한 작업입니다.

### 3. 교체 전에 기존 동작을 고정합니다

라이브러리나 내부 구현을 바꿀 때는 현재 동작을 테스트로 먼저 기록합니다. [Chrono에서 Jiff로의 전환](experience/cluml.md)에서는 기존 타임스탬프 처리 결과를 고정한 뒤 구현과 의존성 정리를 나누고, 영향받는 화면과 서버 호환성을 함께 확인했습니다.
