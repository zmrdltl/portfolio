# 개발 원칙

저는 제품 개발에서 구현 전에 도메인 배경, 운영 정책, 책임 범위, 검증 기준을 먼저 문서화하고, 구현 뒤에는 테스트와 리뷰로 동작을 고정합니다. AI-assisted development에서도 목표는 코드 생성이 아니라 같은 기준으로 산출물을 검증 가능하게 만드는 것입니다.

## 핵심 원칙

- 반복 구현의 허들이 낮아질수록 문제 정의와 검증 기준이 중요해집니다.
- 문서화는 부가 산출물이 아니라 배경 습득과 판단 기준 고정을 위한 도구입니다.
- context, test, review 기준이 명확해야 사람과 AI agent가 같은 방향으로 구현하고 리뷰할 수 있습니다.
- 반복 구현 시간이 줄어드는 만큼 도메인 이해와 코드 리뷰에 더 집중해야 합니다.

## 작업 흐름

```text
도메인 지식과 요구사항
-> 배경, 운영 정책, 예외 정책
-> context, 하지 않을 일, 완료 기준
-> 구현 계획과 test harness
-> 구현
-> review, regression check, 운영 정리
```

## Context

- 기능이 생긴 배경과 사용자 흐름
- 운영 정책과 예외 정책
- 코드 경계와 책임 범위
- 성공 조건과 하지 않을 일
- 실패 시 확인할 로그, 테스트, 재현 절차

## Harness

- 비즈니스 로직의 핵심 동작과 예외 흐름을 테스트로 고정합니다.
- 회귀 가능성이 있는 경로는 샘플 입력, 재현 절차, 검증 명령으로 남깁니다.
- 데이터 정합성, 시간 처리, serialization, API compatibility는 별도 확인 항목으로 둡니다.
- 구현 결과가 완료 기준을 만족하는지 재확인합니다.

## Review

- 변경 범위가 문제 범위를 넘지 않았는지 확인합니다.
- 책임 분리, 일관성, 확장성, 응집도와 결합도를 봅니다.
- 기존 API, 설정, 직렬화 구조, 사용자 흐름과 호환되는지 확인합니다.
- 테스트가 실제 위험 경로를 닫는지 봅니다.
- 새 복잡도가 문제 해결에 필요한 수준인지 판단합니다.

## 도메인 학습

No-code 플랫폼에서는 설계 정보를 SQL, DDL, Java service code, 데이터 동기화, 변경 이력으로 변환했습니다. AI-assisted development에서도 도메인 지식과 요구사항을 context, test, review 기준으로 바꾸는 일이 중요합니다.

## 피해야 할 방식

- 테스트 없는 AI-generated code 병합
- 성공 조건 없는 prompt
- 하지 않을 일을 정하지 않은 구현 지시
- 회귀 위험 설명 없는 대량 변경
- 도구 이름만 앞세우는 설명
